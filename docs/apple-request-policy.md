# Apple 请求风控检查（2026-10-19）

## 核查结论

当前代码依靠减少请求与被拒后等待来降低触发频率，不保证绕过 Apple 风控。未对 Apple 连发请求或测拦截阈值。

| 措施 | 当前实现 | 边界 |
| --- | --- | --- |
| 查询入口 | `/shop/retail/pickup-message` | 接口今后仍可能变化 |
| 请求合并 | Windows 按 location 合并目标，商品编号去重 | Android 目前单目标 |
| 节流 | 客户端至少间隔 60 秒，串行执行 | Windows / Android 不共享预算，同一 Wi-Fi 合计仍可能触发限制 |
| Cookie 会话 | 首次访问购物袋页并复用 Cookie | 不是解验证码，也不保证会话被接受 |
| 403 / 541 | 返回未知并停止请求 15 分钟 | 是本工具策略，不是 Apple 承诺的恢复时间 |
| 429 | 尊重 Retry-After，最少等待 2 分钟 | 无效字段回退最少等待；长等待可取消 |
| 重启 | Windows 冷却单独落盘；Android 已保存查询后的 nextAllowed | 不提供跨设备或全网出口同步 |
| 浏览器特征 | 当前使用常见 User-Agent / Referer / Accept | 未实现 Chrome TLS 或 HTTP/2 指纹模拟，换请求头不保证放行 |
| 代理轮换 | 未实现 | 不提供代理或自动切换出口 |

## 本次修复

1. Windows 与 Android：购物袋暖场已收到 403 / 541 / 429 时，直接进入冷却，不再追加库存请求；手动重查同样不能穿透。
2. Windows：冷却保存到配置目录下的 `request-cooldown.txt`，进程重启后恢复；记录损坏时保守等待 15 分钟。写入失败时停止本次查询。
3. Windows：Retry-After 原始字段容错解析，避免异常字段导致监控崩溃；极长等待拆为可取消的分段等待。
4. Android：修复 Retry-After 秒数乘法溢出；不再把服务器要求超过一天的等待强行缩短为一天。

## 上游对照

检查了本地 `upstream/crates/apw-core/src/apple.rs` 及在线 [CLI 文档](https://github.com/ENCHIGO/apple-pickup-watcher/blob/main/docs/cli.md)。上游采用同地点合并、令牌桶预算、分级冷却和探测；另有代理线路与浏览器传输特征适配。其“约 30 次请求触发拦截”等描述来自维护者特定网络的实验，不能视为 Apple 公布的固定规则，也未在本次重新验证。

本工具比上游的突发预算更简单：不允许连续发出多次库存查询，而是全局每次至少间隔 60 秒。两端同网同时监控时，预算仍独立，无法保证出口合计不触发风控。

- Android：24 项库存 JVM 检查及 10 项超级岛参数检查通过，包含三个暖场拒绝状态与长 Retry-After 边界。
